# ADR 0004 — HTMX para a camada web em vez de SPA separada

**Status:** aceito
**Data:** 2026-05-08

## Contexto

A camada web do MVP do MoodTrack é predominantemente CRUD com fluxos lineares:
registrar humor, ler timeline, abrir prontuário, ler briefing, marcar
consentimento. Não há requisitos de offline, manipulação local pesada de
estado, ou interações altamente interativas (drag-and-drop complexo, editor
colaborativo, dashboard com 50 widgets sincronizados).

Os requisitos reais que importam:
- Sessions server-side (cookies + CSRF) — política de segurança sensata para
  dados clínicos.
- Renderização rápida no primeiro carregamento — paciente abrindo o app no
  celular em conexão ruim deve ver o formulário de registro de humor em
  segundos.
- Time pequeno, expertise principal em Python/Django — manter dois codebases
  (Django + frontend SPA) drena energia que deveria estar na camada de IA e
  privacidade.

O app mobile (React Native) entra em v2 e consome a API DRF separadamente —
ou seja, a API REST existe de qualquer maneira. A questão é apenas: no MVP
web, vale a pena manter SPA separada que consome essa API?

## Decisão

Camada web do MVP é **Django Templates + HTMX + Alpine.js + Tailwind CSS**.
Sem build pipeline JS separado. Sem framework SPA. DRF existe como API REST
para o futuro app mobile e para endpoints específicos quando útil, mas não é
o caminho principal de renderização web.

## Alternativas consideradas

- **React/Next.js como frontend separado consumindo DRF.** Padrão moderno,
  excelente DX em equipes JS, mas:
  - Dois codebases, dois deploys, dois sistemas de auth (com a complexidade
    de manter cookies vs JWT em sincronia para um app sensível).
  - Build pipeline (npm, bundler, lint, test, type) que precisa ser mantido.
  - Para fluxos CRUD simples, esforço é desproporcional ao ganho de UX.
  - Time ficaria dividido entre Python e TS no MVP.
- **Página renderizada full reload, sem HTMX.** Funciona, mas torna pequenas
  interações (atualizar uma seção, abrir modal) frustrantes. HTMX entrega
  90% da fluidez de SPA com 5% do código.
- **Livewire/Phoenix LiveView estilo (django-unicorn).** Tecnicamente
  interessante, mas menos maduro e amarra o cliente fortemente ao servidor
  via WebSocket — overhead que não compensa para o MVP.

## Consequências

**Positivas:**
- Um codebase. Auth, sessions, CSRF, permissions — tudo já no Django.
- Sem build JS no caminho crítico do desenvolvimento.
- Server controla estado autoritativamente — alinhado com a postura de
  segurança (não confiar em cliente para visibilidade de registros, autorização
  de vínculo, etc.).
- HTMX + Alpine.js cobrem 95% das interações que o produto realmente precisa.
- Quando uma view exige mais interatividade, dá pra escalar incrementalmente
  com Alpine.js sem reescrever tudo.

**Negativas:**
- UX em telas com muito estado local (rascunho de registro longo, gravação
  de áudio em v2) precisará de mais Alpine.js. Aceitável.
- O app mobile (v2) usa API REST que terá menos cobertura que se a SPA web
  já estivesse consumindo todos os endpoints. Mitigação: sempre que uma
  funcionalidade for nova, escrever também o endpoint DRF correspondente,
  ainda que a web não use.
- Time precisa aprender HTMX (curva curta, mas existe) e disciplinar uso de
  `hx-` attributes para não virar bagunça.
- SEO e perfomance bruta de SPA não são vantagens aqui (a maior parte do
  produto é atrás de login), então essa "perda" não dói.
